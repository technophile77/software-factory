# 0013. Merge conflict resolution

- **Status:** Accepted. Amends ADR 0007 (rebase replaced by merge).
- **Date:** 2026-11-10
- **Decided by:** owner
- **Decision item:** item 15; write-up in `docs/proposals/0015-merge-conflict-resolution.md`

## Problem
ADR 0007 said when to update feature branches, but not who resolves a
conflict. The orchestrator may not edit source (least privilege), and
rebasing would rewrite the engine's per-edit checkpoints (ADR 0012).

## Decision
- After any merge to `main`, the orchestrator merges `main` into every active
  feature branch. It does not rebase. The squash merge (ADR 0005) keeps
  `main` linear.
- The orchestrator classifies each conflicted file and hands it to the role
  that owns it:
  - lockfiles and generated files are regenerated by the software developer;
  - source goes to the software developer;
  - tests go to the test engineer;
  - the feature spec goes to the requirements analyst.

  Each keeps the approved behavior of both sides and records its choices in
  its agent report.
- Change-controlled files are never resolved by an agent; the conflict
  becomes a Configuration hygiene item.
- Verification after resolving: the full test suite and CI, Code Review
  on the resolved hunks, and, if the feature had already passed validation,
  the judge on the resolved hunks. All at the repo's maturity level.
- Escalation goes to the existing inboxes and categories, with titles
  starting "Merge conflict:" and links to both features:
  - changing approved behavior: Testing inbox;
  - two contract changes: Decision inbox, Interfaces;
  - contradictory specs: Decision inbox, Product;
  - three failed cycles: Testing inbox.

## Consequences
- The orchestrator AGENT.md and the workflow are amended through hygiene items.
- Feature branches carry merge commits until the squash merge.
- A feature waiting on a merge-conflict decision pauses; others continue.
