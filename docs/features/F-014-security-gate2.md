## Info

- **Git version (spec deviation, not a security issue).** The reader is `cat-file --batch-command` (git 2.36 and later). Spec §5 says plain `--batch`, "so no new minimum". On an older git the reader exits with a usage error, each read falls back to the plain call, and after three failures per repo the engine stops starting readers there (reasoned). Answers stay right; only the speed-up is lost. Needs an owner decision (below).
- **Trees git reads but the parser refuses (fail closed, availability).** A 7-digit zero-padded mode such as `0100644` (git reads it and fsck only warns) and any entry name that isn't valid UTF-8 make the whole tree unreadable through the reader. Plain git read both (reproduced for the mode). For `populateWorktree`, which lists the whole project tree, one such name anywhere now refuses the worktree. This is SR-5 working as approved; the owner may want to know about the narrower acceptance.
- **Path forms.** `lsTreeEntry("/a")` returns `null` through the reader where `ls-tree` errors, and `lsTree("d/")` or `lsTreeSized(["d/"])` with a trailing slash list less than `ls-tree` (reproduced). `checkRepoPath` and `checkStatePath` refuse these forms before any read, and the other callers pass constants, so neither is reachable.
- **`lsTreeSized` extra entries.** When a requested path runs through a file, link or submodule (`l/x` with `l` a link), the reader lists `l` itself and `ls-tree` lists nothing (reproduced). No `TreeSnapshot` caller looks up a path that wasn't requested, so the result is unchanged.
- **Messages.** Some failures read differently (`"<commit> isn't a commit"` instead of git's own stderr line). Each is fixed text with no internals (S5.2).
- **Held head and tampering (A-1).** The commit retry can't lose data: it re-reads the moved head's tree and changes only the paths it writes, as a fresh read did on `main`. A swap failure clears the held head (SR-8), and `sync()` reads it fresh before `checkRemote` and `checkLocal`. One existing gap is **not new**: a transcript edited locally between syncs is overwritten by the engine's next transcript commit (the whole file is written), so `checkLocal` then sees an intact chain. `main` behaves the same, because it also committed on whatever head it read. It is an F-007 SR-17 limitation, not an F-014 regression.
- **Ref and object parity (reproduced).** Same-name branch and tag, an annotated tag of a tree, short and ambiguous ids, missing refs, refs moved, packed and deleted, `gc --prune=now`, and `repack -ad` all gave the same answers as plain git with the reader kept open. Names outside `NAME_RE` (including `~`, `:`, `..` and newlines) go to the plain call.
- **Windows, `bd3e4b5` (reasoned, not run).** Ending a reader by closing its input is the right fix for Git for Windows' launchers: the real `git.exe` inherits the pipe, sees end of input and exits. A killed launcher alone left it running, which kept the repo folder open (the EBUSY in CI). `close()` waits for the process to exit and kills it after 2 s, and the engine's stop now awaits this. A reader that is hung rather than idle still won't read its input. On Windows the kill after the grace then reaches only the launcher, so the real git can stay, holding pack files, until it finishes. `runFixed` has the same limit for every timed-out git call; it is not new here. `Git.withReaders` is a process-wide set used only by test cleanup (`closeAllReaders`); it holds `Git` objects, not repo data, so SR-4 is unaffected. The idle close (2 s) bounds open pack handles (spec edge case).

## Checked and fine

- **Protocol.** Requests go one at a time per reader through `serial`. A header must match `<id> <type> <size>`, with a 4 KiB line cap, the id equal to the request when the request is an id, and a type the caller expects. `missing` and `ambiguous` are matched against the exact name sent. A body is read only after an `info` within the limit, and then by id, with the id, type and size of the second header compared with the first and a trailing newline required. A short read, an exit, or `close()` during a read reject with `ReaderBroken`, and FR-2's fallback runs. A failure part-way through a multi-object read (`lsTree`, `lsTreeSized`, `catBlobs`) discards everything and redoes the whole call with plain git, so results never mix.
- **Names (SR-2).** `NAME_RE` with no `..` and at most 1,024 characters. JavaScript's `$` doesn't match before a trailing newline, so command injection into the batch is refused (tested).
- **Overrides (SR-2).** The reader runs `gitPath` by absolute path, with `shell: false`, `-C cwd`, `overrideArgs`, and the same `env()` as every git call. `--batch-command` without `--filters` or `--textconv` applies no filters, as `cat-file blob` didn't.
- **Children and timeouts (SR-7).** Every reader pid is added to `Children` and removed on `close` or `error`. Each read has the 120 s timeout of `run()`. A timed-out reader is ended (input closed, killed after 200 ms), and its read rejects at once, so the fallback can run before the process is gone (M2).
- **Modes (SR-1).** `canonMode` matches git's `canon_mode` for regular files, links, trees and submodules (`100664` → `100644`). Every other type is refused where git would show it as a submodule, which is stricter. `readBlob`, `readFileAt`, `readDirAt` and `TreeSnapshot` still refuse non-regular entries. Links and submodules as parents read as missing, as before (tested and reproduced).
- **L7 (SR-3).** `refuseRedirectingConfig` still runs, unchanged, before every push and fetch. Only its output is reused.
- **Caches (SR-4, SR-8).** Readers are per `Git` and per folder, and closed at stop. Master facts are per `Git` instance (a `WeakMap`). The held head is per `StateRepo` and cleared before `worktree add`, on a failed swap and on `forgetHead()`. Nothing is written to disk.
- **State worktree reads.** `ensureWorktree` and `fastForward` now read `STATE_REF` or `to` through the main checkout instead of the new worktree's `HEAD`. These are the same commit, and `to` is exact even if the ref moves.

**About the M2 regression test.** The new test ("output a timed-out reader writes later never reaches the next reader") passes with the guard removed. Its stand-in writes its late line from the reader process itself, and the immediate `SIGKILL` stops that process before it writes. So the test checks the kill, not the guard. That is not enough as a regression test. The guard and the listener removal protect against output that git wrote **before** the kill but Node hadn't read yet, and the kill can't prevent that. Recommended: make the stand-in write its late line from a background process that outlives the kill (`( sleep 0.05; echo "<id> commit 5" ) &`, as in probe 4), and follow it with a read by ref. That test fails only when both protections are removed, so it guards against a future change dropping them. Low (S7.1), non-blocking.

**Windows (reasoned, not run).** `breakOff` now destroys stdin before the kill, so a real `git.exe` behind a killed launcher still sees end of input. Its later output goes nowhere, because the stream is still flowing with no listener, so it can't block on a full pipe. `close()` keeps the graceful end for the idle and stop paths that fixed the EBUSY failures.

### Checked and fine

- **No forged times.** Creation time is set by the kernel. A process can't choose its own creation time, its parent's, or the number recorded as its parent. A named parent (`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`) must exist at creation, so it is older. Apart from L8's clock step, a cut happens only when the recorded parent pid names a different, younger process. That means the real parent has exited, and the walk already admitted that case.
- **Unknown times fail closed.** `startedAfter` cuts only when both times are known. `startedAt` returns null for pid ≤ 0, for a process that can't be opened (System, protected processes, another user's), or when `GetProcessTimes` fails. `osStartedAt` turns any throw into null. Null keeps the plain ancestry answer (probe: unknown times, still refused), so an FFI failure never admits more than the walk without start times (SR-15). The parent lookup still throws on failure, and the peer is refused, as before. `OpenProcess`'s NULL on failure is caught by `invalid()`, and the handle is closed in `finally`.
- **Races.** If the parent exits and its pid is reused between the snapshot and `startedAt`, the walk cuts. That parent has gone, and once the engine handled its exit the walk would have admitted that orphan anyway (L9 (a)). If `cur` is reused in that window, its time gets later and nothing is cut. A client listed as our own child is still refused before any time is read (`:39`). The walk is synchronous, so `exit` handlers can't run during it, and `lastChain` belongs to the refusal it is logged with.
- **FILETIME to Number.** Values near 1.34×10¹⁷ round to a multiple of 16 (1.6 µs). Rounding never reverses an order, so a rounded "parent later" means the parent really was later. A tie doesn't cut (probe: `…001` and `…009` both round to `…000`).
- **PID 0 and 4.** `startedAt` refuses pid ≤ 0. The loop stops at `cur ≤ 1`. System (4) started at boot, so it never looks younger than its child.
- **Linux and macOS.** `osStartedAt` gives `undefined`, so no cut happens. Only change 3 and the `exit` removal apply. On Linux a zombie child still has `/proc/<pid>/stat`, so its children are still refused until the engine reaps it. On macOS an exiting parent's children are reparented to launchd at exit, so they were already admitted (L9 (a)).
- **Peer pid unknown (Unix).** It is now its own refusal with its own message. It still refuses.
- **Log (S3.3, S1.2).** The pid list is logged only after the uid or SID check has passed, so it holds only the owner's own process ids. It holds at most 65 integers, with no names, paths or command lines. It goes to the engine's log and not to the client.
- **FFI list (SR-15).** `GetProcessTimes` is declared in `FUNCTIONS` and loaded only in `ffi.ts`, and no other module imports koffi (existing test). `PROCESS_QUERY_LIMITED_INFORMATION` is the least access that works.
- **Tests (S7.1).** The new unit test covers a reused pid held by a child and by a grandchild, unknown times, a listed pid that has gone, and a lookup that throws. On Windows it checks the real lookup against this process and its parent. Not tested: the `exit` removal in `runFixed` and the reader, and L8's clock step (Low, non-blocking).

**Verdict for this change: PASS.** No Critical, High or Medium findings, and 2 Low (L8, L9), neither blocking at Rapid prototype. The change doesn't let an engine-started process do anything it couldn't do at `70af2af`: every new admission is a peer whose recorded parent has exited, or L8's clock step, which needs a privilege agents don't hold. Fail-closed behavior on lookup failure (SR-15) holds. L9 needs an owner decision to correct F-007's recorded residual risk.
