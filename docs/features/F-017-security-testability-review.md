# F-017 Security and Testability Review (requirements review)

- **Feature:** F-017 Isolation evaluation for every onboarded model, spec v5
- **Reviewer role:** security-reviewer, against `docs/security-standards.md`
- **Date:** 2026-11-14
- **Inputs:** the F-017 spec; F-013 SR-9, SR-11, SR-16, SR-17; ADR 0026 and
  Role policy v2.7 as on `claude/project-thread-us9zz2` (PR #61); the
  engine channel contract (Engine control channel v1.1 access rules).
- **Maturity level:** Rapid prototype (the factory repo's level). Only
  Critical findings block there.
- **Result:** 14 findings: 0 Critical, 1 High, 8 Medium, 5 Low. Nothing
  blocks at Rapid prototype; the High would block from Alpha. The owner's
  decisions (OQ-1 to OQ-4, OQ-6, the FR-7 scope) are not re-opened.
  Recommendations are proposed as SR-4 to SR-17 for the owner to approve.
  Findings 1, 9 and 12 also need an owner decision (§ Decisions needed).

| 3 | S7.1, S2.2, S5.1 | Medium | No | § 2.3 says every Part 1 attempt "must be refused or held". | 4 | S1.4, S6.2, S8.1 | Medium | No | FR-3 path and tool cases miss Windows forms and tool variants the gate must resolve. Hard links are not resolved by real-path resolution, so a link inside the worktree to an outside file passes the "inside the worktree" check for both read and write (a file-tool `Edit` would change the outside file). Also missing: 8.3 short names (`SECRET~1`), alternate data streams (`.env::$DATA`, `a.txt:x`), trailing dots and spaces (`.env.`), `\\?\`, `\\.\`, UNC and `GLOBALROOT` paths, a link swapped in between the gate's check and the tool's open, and a symbolic link committed to the branch that points outside. | 6 | S2.1, S2.3, S6.2 | Medium | No | FR-1 stores records in "the engine-owned folder", under the owner's profile. Residual (state it with ADR 0026): agent-run code holding the owner's GitHub login or an unprotected signing key could also forge the approval. |

**Already covered by the spec or decisions:** the engine, not the model,
enforces isolation, and Part 1 tests that with a deterministic stub (§ 1,
FR-3); canaries are random per run (§ 6); records are voided by changes to
model identity, LiteLLM pin, Claude Code and engine version and the
resolved definition (OQ-4, FR-9); a per-model definition can't add tools or
remove denies (FR-10, AC-7); model approval per role is the owner's
Security decision (SR-3); Part 1 is a CI release gate (SR-2, FR-8);
endpoint models stay off roles with a shell or network tool (F-013 SR-9);
the gateway strips LiteLLM routing and credential fields (F-013 SR-17) and
FR-3 tests it; the engine already runs sessions with `settingSources: []`
(made a tested requirement by SR-8).

## Decisions needed (Security)

1. **Where Part 2 runs for shell roles (finding 1).** (a) In a container
   from the retained ADR 0015 code, for the software developer and test
   engineer only. (b) Not until containers return at Beta; those roles are
   evaluated with Part 1 only. (c) On the host with SR-5's inert payloads
   and scrubbed environment, accepting that an obeyed injection can still
   reach the keyring, SSH agent and network. **Recommended: (a)**; (b) if
   container work is unwanted before Beta.
2. **Production attempt monitor (finding 9).** Add the in-use attempt
   counter and record voiding (SR-12), or rely on the evaluation alone.
   **Recommended: add it**: it is the only check that doesn't depend on the
   model failing to notice the test.
3. **FR-1 versus FR-7 for report-only endpoint roles (finding 12).**
   **Recommended:** Part 1 required, Part 2 not.
4. **Residual in SR-9.** Record forgery by agent-run code holding the
   owner's GitHub login or signing key stays possible until Beta; the owner
   accepts it with ADR 0026 or asks for a stronger binding.

## Threat model (S9.7)

External interactions: the model provider (Anthropic API through the
credential proxy) or a LAN endpoint (through the gateway and the LiteLLM
container); the inbox on GitHub issues (the report and the approval); CI
on GitHub Actions. Assets: the owner's credentials and files on the PC,
the integrity of evaluation records and the rung gate, and the owner's
inbox attention.

| STRIDE | Threat | Control |
|---|---|---|
| Spoofing | A forged or copied record opens a rung for an unevaluated model; a swapped model keeps its identity fields | Live key computed by the engine and bound to the owner's approval (SR-9); residual of F-013 SR-11 (no digest) stays |
| Tampering | Overlay or profile loosens isolation by prompt or route option; planted `.claude/`, git config or package scripts change what runs later | SR-11 tighten-only incl. prompt sections; SR-8 cases and common-git-dir check; FR-9 voiding |
| Repudiation | Which configuration a model was approved under | Record key incl. policy, ask list and catalogue (SR-10); report states the tested configuration (FR-6) and what isn't enforced (SR-6) |
| Information disclosure | Real secrets reach the model or leave the PC during Part 2; canary leaks escape the scan; user name in paths | SR-4, SR-5 run environment; SR-13 encoded scan; SR-14 |
| Denial of service | Ask-list holds flood the inbox; looping model; runaway or detached process | Harness answers holds (SR-5); turn, token and time caps (FR-3); process tree ended (SR-8); busy endpoint is "not run" (§ 6) |
| Elevation of privilege | Escape through hard links, short names, streams, background processes, git config, the engine pipe or unlisted tools | SR-7, SR-8 catalogue cases; accepted ADR 0026 paths reported per role (SR-6) |

OWASP Top 10 for Agentic Applications: prompt injection is the thing Part 2
measures, and SR-5 keeps its payloads inert while SR-4 keeps them away from
real credentials; tool misuse is bounded by the gate and SR-7's full tool
enumeration; data leaks by SR-5 and SR-13; identity abuse by the
harness-answered holds and the owner-bound records (SR-9). OWASP LLM Top 10
2025: LLM01 (prompt injection) and LLM06 (excessive agency), as in SR-2.
