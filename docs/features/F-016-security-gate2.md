## Info

- **Workflow template (H-0162, F-011 SR-12).** It has `permissions: issues: write` only and no third-party action, so there is nothing to pin. It runs on `repository_dispatch` type `factory-inbox` only. The payload reaches the shell only through `env` (`toJSON(client_payload)`) and `jq`. The item id and revision are checked by regex before being used in a `jq` filter, and the issue number before use. Comments must start with this item's marker and are length-capped, and labels must match a fixed pattern. A new revision posts only on an issue opened by `github-actions[bot]` whose body starts with this item's marker. Nothing from the payload is executed. Only a token with write access to the config repo can send the dispatch.
- **Who can trigger an effect.** Reactions count only from the pinned owner id, and only `+1` on a bound action comment or `rocket` on the latest confirm comment. Action comments are bound only when the issue body hashes to the rendered body and every comment is a `github-actions[bot]` Bot comment equal byte for byte to the rendered one. Comments and reactions on earlier revisions are refused as stale. A command counts only from the owner, unedited, and not on an engine or action comment (SR-17). Engine comments start with `Confirm:`, `Recorded:`, `Not recorded:`, `Stale:` or `Reopened:`, never `/`, and this holds even when a crash loses an engine comment's id. Risky actions (every Security choice, and every spec, hygiene and maturity Approve) go through a confirm bound to the revision and to a 15-minute window measured both at read time and at reaction time. The confirm code is 4 characters from a 32-letter alphabet with no modulo bias. All of this holds for answers read from GitHub. M1 is about the records once they are written.
- **Token for a pins-stopped project (OQ-3).** The token is looked up under the pinned project name (`engine.ts:489-495`), never the changed manifest's, and the inbox reads actions only from the pinned owner id. Such a project doesn't go through `authorizeProject`, so the config repo the inbox talks to is the local clone's `origin`, checked only by `refuseRedirectingConfig` and the privacy check (private, owner as the only collaborator). That is enough for its purpose, because the token is the owner's own and the repo is the owner's local clone.
- **Orchestrator turn and session (SR-11).** The first turn holds only engine values: feature id, a spec path checked against `specPathPattern`, version, commit and report path. It tells the agent the spec is data. The policy is narrowed to Read, Grep, Glob and Write, with no commands or network, and write is only the named report. The report folder is engine-owned. Any other file in it, or any change in the worktree, is a breach, and nothing is committed. Code checks run first, and a pass from the agent never overrides a failed code check. The implementation still runs the session in a container through the Gate 1 runner, which is stricter than SR-11 v11 needs. When the worktree thread moves sessions to the host (ADR 0026), SR-11's file-tool rules and end-of-session write check have to carry the same guarantees on their own.
- **Analyst return turn (SR-2).** Owner notes, reviewer labels and readiness evidence go in as a JSON block after the engine's instructions, labelled as data. The framing line calls the contents "the owner's own words and the engine's checks". In fact the option labels come from the security reviewer and the `readiness_failed` evidence from the orchestrator agent, so the label overstates how far they can be trusted. Suggested wording: "the owner's notes, the reviewer's labels and the readiness gate's evidence".
- **OS notifications.** The notifier calls fixed binaries (`/usr/bin/notify-send` or `/bin/notify-send`, `/usr/bin/osascript`, `%SystemRoot%\…\powershell.exe`) with argv only and no shell. Text reaches it only through environment variables or argv, with control characters stripped and a 200-character cap. On Windows the text is XML-escaped before `LoadXml`, and PowerShell's interpolation doesn't evaluate the value. On Linux, notification servers render a small markup subset (`<b>`, `<a href>`, `<img>`) in the body. The text is item titles and engine words, so the impact is cosmetic. Escaping `<` and `&` for the Linux case would close it.
- **Migration script (F-011 FR-16, SR-20).** It carries only open items. It re-renders all old text as fenced outside text through the normal filing path, which includes the secrets scan, and removes the old file in the same commit. It never overwrites an existing record. It drops every old owner action and notes that it did, which is stricter than SR-20 allows (signed actions could be kept). The owner should know that answers given before migration have to be given again. It handles one `--project` per run, so managed repos' `factory/state` (FR-16) need one run each. See L1 for the effect it infers.
- **GitHub responses.** `HttpIssues.call` reads the whole body before checking the 4 MiB cap (`github-issues.ts:111-112`). GitHub is the only host, and redirects are refused, so this is noted only.
- **Readiness sign-off binding (SR-3).** Approve checks that the branch head still equals the commit stored on the feature's chain at filing, not the record's effect. A moved branch withdraws the sign-off and runs the gate again. This holds, subject to M1 for forged records.

## Permissions
No new permission beyond what the spec states: the factory token's Issues read and write on the config repo (F-016 SR-9, F-011 SR-1), and the workflow's `issues: write`. No new dependency. Agents get no GitHub credential. The orchestrator gets read-only tools and a single report path.

## Needs the owner's decision
- **M1, Security:** whether the engine must re-verify each recorded owner action on GitHub before its effect runs, and whether to refuse remote `inbox/` changes as it refuses remote `interviews/` changes. Recommended: both. The alternative is to accept as a residual risk, stated in F-016 section 9, that a writer of `factory/state` can act as the owner.
